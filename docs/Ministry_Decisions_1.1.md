# Министерство культуры — реестр продуктовых и архитектурных решений

**Версия:** 1.1
**Дата фиксации:** 16 октября 2026
**Проект:** SecretH → «Министерство культуры» (Telegram Mini App)
**Статус:** решения владельца продукта после GAP-анализа; не означает, что функции уже реализованы.

## 1. Приоритет документов

1. `docs/Ministry_TZ_Functional_1.1.md` — целевые функциональные требования.
2. `docs/Ministry_TZ_UI_UX_1.1.md` — целевые требования к интерфейсу.
3. `docs/Ministry_Decisions_1.1.md` — уточнения и согласованные решения после GAP-анализа.
4. `docs/SPEC.md` — **архив требований прежнего SecretH**, а не источник истины о будущем поведении при конфликте.
5. Исходный код, миграции и тесты — источник сведений **о текущей реализации**, но не автоматический источник продуктовой нормы.

Оба новых ТЗ и этот реестр должны читаться вместе. При конфликте двух целевых документов не выбирать поведение молча: вынести расхождение на решение владельца. Уже обнаруженное расхождение о RUIN-рейтинге исправлено в версии 1.1.

## 2. Утверждённые решения

| № | Область | Решение | Последствие для реализации |
|---:|---|---|---|
| 1 | Целевой продукт | Новый SecretH называется «Министерство культуры», Telegram Mini App — основной интерфейс | Нужны HTTP API и новый frontend |
| 2 | Старый бот | После перехода только запуск приложения, ссылки-приглашения, уведомления | Не оставлять два независимых пути создания/исправления игр |
| 3 | Исходный проект | Развиваем существующие сервисы, доменную логику и тесты; не делаем rewrite | Переиспользование backend, PostgreSQL, SQLAlchemy, проверок ролей/побед |
| 4 | Источники требований | Новые ТЗ 1.1 приоритетнее `docs/SPEC.md` | Старый SPEC сохранить для истории и регрессии |
| 5 | Рабочие данные | Начать с **новой чистой PostgreSQL**, без переноса существующих партий SecretH | Старую БД проверить, забэкапить, испытать restore в тестовой БД; не удалять |
| 6 | Историческая статистика | После самостоятельной регистрации всех игроков администратор вручную импортирует историю из прежней таблицы | Нужен маппинг к зарегистрированным участникам без создания дублей; формат источника ещё неизвестен |
| 7 | Регистрация | Без поиска/привязки исторического Player во время регистрации | Не реализовывать historical linking approval flow для нового onboarding |
| 8 | Статусы участников | Активен: просмотр + игра; неактивен: просмотр клуба/профилей/рейтингов без новых игр; заблокирован: нет доступа | Единая модель статусов и авторизации |
| 9 | OWNER | Единственный владелец клуба; назначает/снимает ADMIN | Отдельная серверная роль и проверки |
| 10 | Bootstrap | Оператор CLI создаёт клуб и первое одноразовое приглашение; пользователь регистрируется; отдельная CLI назначает его OWNER | Без автоматического OWNER для первого зарегистрированного |
| 11 | Создание вечера | Только ADMIN/OWNER, с начальным составом и назначением кандидата | Изменить старое правило «любой участник может начать» |
| 12 | Статистик | Кандидат обязательно принимает/отклоняет, до согласия нельзя записывать партии | Pending assignment; UI две кнопки внутри карточки |
| 13 | Передача | Старый статистик сохраняет полномочия до принятия новым | Атомарная смена после согласия |
| 14 | Аварийная смена | **Убрать** процедуру смены двумя участниками | Вывести `StatisticianRecovery` из активных сценариев, оставить исторический аудит |
| 15 | Повторное открытие | Только ADMIN/OWNER, нет другого pending/active вечера; фойе пусто; новый кандидат должен согласиться | Сохранить вечер и номера партий, не создавать дублей |
| 16 | Периоды вечера | Хранить все периоды открытия и завершения, но показывать детали только ADMIN/OWNER | История периодов и аудит reopen |
| 17 | Выбор игроков | 5–10, можно добавить отсутствующего игрока без изменения его присутствия | Обновить ограничение при менее пяти присутствующих |
| 18 | RUIN | Новые отметки только при первом сохранении партии, вместе с ней; затем лишь правки/удаление имеющихся | Атомарная финализация Game + RUIN; старые события только legacy |
| 19 | Архивная партия | ADMIN/OWNER могут редактировать и аннулировать архив в любое время без reopening | Бизнес-права не должны зависеть от finished status для администрации |
| 20 | RUIN в архиве | ADMIN/OWNER могут менять или удалять существующие RUIN без reopening | Запрет *добавления* новых RUIN сохраняется и для OWNER |
| 21 | Полномочия статистика | Исправляет игру, VOID и существующие RUIN только в своём активном вечере | Сервер проверяет session-level права |
| 22 | Restore партии | Только ADMIN/OWNER, включая архив, без reopening | Inline-подтверждение, нет обязательной причины, пересчёт статистики |
| 23 | Ролевой рейтинг | Частота выпадения роли, а не winrate | Новый расчёт и тесты |
| 24 | RUIN-рейтинг | Количество RUIN по убыванию; при равенстве **меньше действующих партий — выше** | Исправлена несовместимая формулировка старого UI/UX ТЗ |
| 25 | Audit | Успешные изменения + существенные отказы безопасности; **не** ошибки заполнения форм | Понадобится безопасный аудит отказов без секретов |
| 26 | Полное восстановление PostgreSQL | **Только операторская CLI-команда**, в Mini App — инструкция | Не создавать API endpoint полного restore БД |
| 27 | XLSX | Экспорт и dry-run/import остаются внутри административной панели | Перед импортом явное `ПОДТВЕРЖДАЮ` |
| 28 | Блокировка черновика | Бессрочная, без TTL; захват одним редактором; перехват ADMIN/OWNER | Серверный владелец и version, без expiration job |
| 29 | Сохранение шага | При «Далее» и «Назад»; **не** на каждом изменении поля | Не переходить без успешного ответа сервера |
| 30 | Статус шага | Постоянный: «Есть изменения», «Сохранение…», «Сохранено», «Ошибка сохранения» | Значение «Сохранено» — только после commit/ack |
| 31 | Выход | Явное «Сохранить и выйти» сохраняет шаг, затем освобождает lock; «Остаться» сохраняет редактирование | Закрытие Telegram не освобождает lock |
| 32 | Хранение черновиков | Бессрочно до финализации или ручного удаления, включая завершённые вечера | Никаких auto cleanup/TTL |
| 33 | Удаление черновика | Текущий редактор, ADMIN или OWNER с подтверждением и аудитом | Уже записанные партии не трогать |
| 34 | Черновик в фойе | Компактный служебный блок над сохранёнными партиями | Видят только действующий статистик, ADMIN/OWNER |
| 35 | Черновик в архиве | Отдельный служебный блок в карточке закрытого вечера | Видят только ADMIN/OWNER; редактирование до reopening недоступно |
| 36 | Передача старого черновика | При reopening блокировка остаётся у прежнего редактора до явной передачи ADMIN/OWNER | Назначение нового статистика не меняет владельца lock |
| 37 | Персональные итоги | При изменении архивных партий переслать сводку только затронутым адресатам, если меняются ранее отправленные итоги | Версионирование/dedup уведомлений |

## 3. Специальные условия перехода

- Новый чистый production-клуб и старая сохранённая БД — разные наборы данных. Новые пользовательские UUID появляются в новом клубе; старые игровые записи **не импортируются автоматически**.
- Из старой таблицы статистики история импортируется позже; до получения её образца **не придумывать столбцы, маппинг и конвертер**. Сначала спецификация сопоставления + dry-run; затем импорт.
- Само решение о чистой базе **не отменяет** нужду в миграциях, тестах целостности и безопасных схемах обновления для будущего production.
- Старый бот во время постепенного перехода может ещё работать с прежними данными в отдельном окружении; нельзя оставлять два несовместимых mutation-интерфейса одновременно на новой базе.
- Права и чтение секретных данных черновика должны проверяться на backend, не только скрытием блока Mini App.
- Не назначать OWNER и не выдавать первое приглашение из общедоступного интерфейса; только защищённые операторские действия.

## 4. Ещё не согласованные технические параметры

Эти параметры **не утверждать молча**:

1. Максимальный размер XLSX и резервных файлов.
2. Срок действительности `initData` и серверной web-session, детали ротации токенов.
3. Границы допустимых целых значений четырёх порогов рейтинга.
4. Модель версий XLSX (исходный 5-листный формат и возможная v2) и правила обратной совместимости.
5. Конкретная схема периодов вечера, версионирования сводок и календарные правила `Asia/Yakutsk`.
6. Интервалы retries/количество попыток/порог эскалации для outbox.
7. Технические способы ручного перехвата и диагностики зависших бессрочных блокировок.
8. Маршруты API, интерфейсные пакеты, инфраструктура и последовательность CI/CD.
9. Структура и соответствие столбцов **фактической** внешней статистики для исторического импорта.

## 5. Что Codex не должен делать автоматически

- Не удалять `docs/SPEC.md`, старую базу, историю или аудиторские записи.
- Не считать макеты доказательством реализованного Mini App.
- Не переписывать с нуля роли, валидацию побед или схему Game без обоснования.
- Не включать REST-операцию восстановления PostgreSQL по старому тексту UI/UX 1.0.
- Не создавать интерфейс `StatisticianRecovery` из прежнего кода.
- Не подменять новый RUIN-рейтинг старой долей игр с RUIN или ролевые частоты победами в роли.
- Не внедрять TTL/автоочистку для черновиков и lock.
- Не приступать к массовой реализации до проверки текущей тестовой базы и согласования плана изменений.
