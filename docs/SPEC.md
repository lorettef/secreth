# Техническое задание

## Telegram-бот для статистики игр Secret Hitler

**Версия:** 1.0
**Статус:** MVP specification
**Основной интерфейс:** Telegram Bot
**Язык первой версии:** русский
**Тип проекта:** приватный бот для постоянной компании игроков

---

# 1. Цель проекта

Создать лёгкого Telegram-бота для ведения статистики регулярных игр в Secret Hitler.

Главный принцип продукта:

> После окончания партии статист должен иметь возможность записать результат примерно за 20–30 секунд и несколько нажатий.

Бот НЕ должен превращать игру в ведение подробного протокола.

Не нужно записывать:

* кто был президентом каждого раунда;
* кто был канцлером каждого раунда;
* кто за кого голосовал;
* какие карты кому пришли;
* какие карты сбрасывались;
* кто кого номинировал;
* историю каждого правительства;
* трек выборов;
* последовательность принятых законов.

Храним только информацию, которая нужна для долгосрочной статистики и истории компании.

---

# 2. Основные сущности продукта

Система строится вокруг следующих сущностей:

**Клуб → Игроки → Игровые вечера → Партии → Роли → Результаты → События**

Клуб — постоянная компания игроков.

Игровой вечер — одна встреча компании, например субботняя встреча.

Партия — одна завершённая игра Secret Hitler.

Состав игрового вечера может изменяться в течение вечера:

* кто-то пришёл позже;
* кто-то ушёл домой;
* кто-то пропускает следующую игру.

Каждая партия должна навсегда сохранять именно тот состав игроков, который участвовал в этой конкретной партии.

---

# 3. Основные продуктовые принципы

## 3.1. Минимум ручного ввода

Если бот способен вычислить значение самостоятельно, пользователь не должен его вводить.

Примеры:

* количество Fascists определяется количеством игроков;
* количество Liberals определяется автоматически;
* победившая команда может проверяться по типу завершения игры;
* Liberals определяются как все игроки, которые не являются Hitler/Fascist;
* номер партии внутри вечера присваивается автоматически.

## 3.2. Работа кнопками

Основной UX — Telegram inline-кнопки.

Текстовые команды допустимы как вспомогательные, но пользователь не должен быть обязан помнить `/addgame`, `/stats` и подобные команды.

## 3.3. Одна ответственная персона за ввод

Во время конкретного игрового вечера изменения вносит:

* статист вечера;
* либо администратор клуба.

Обычные игроки имеют read-only доступ.

## 3.4. Админ не нужен для начала игры

Если администратор не приехал, любой зарегистрированный игрок клуба может начать новый игровой вечер.

Создавший вечер игрок автоматически становится статистом вечера.

## 3.5. История не должна ломаться

Изменение текущего состава не должно изменять состав уже сохранённых партий.

Статистика всегда вычисляется из партий.

Не создавать отдельные вручную обновляемые поля вроде:

`player.total_wins += 1`

Источником истины являются записи партий.

# 4. Роли пользователей

В системе три основных уровня доступа.

## 4.1. PLAYER — обычный игрок

Может:

* открыть текущий игровой вечер;
* увидеть текущий состав;
* увидеть количество сыгранных партий;
* увидеть счёт Liberals/Fascists;
* смотреть свою статистику;
* смотреть статистику других игроков;
* смотреть рейтинги;
* смотреть историю завершённых партий;
* смотреть историю игровых вечеров.

Не может:

* записывать партии;
* менять состав;
* назначать роли;
* добавлять события;
* редактировать результаты;
* удалять игры;
* управлять игроками;
* назначать администраторов.

---

## 4.2. STATISTICIAN — статист игрового вечера

Это не постоянная глобальная роль.

Статист назначается конкретному `game_session`.

Статист может:

* записывать новую завершённую партию;
* выбирать Hitler;
* выбирать Fascists;
* записывать победителя;
* выбирать способ завершения;
* добавлять игровые события;
* добавлять Руины;
* менять текущий состав вечера;
* отмечать пришедших;
* отмечать ушедших;
* исправлять партии текущего активного вечера;
* передавать роль статиста другому игроку;
* завершать игровой вечер.

Статист НЕ может:

* редактировать старые вечера;
* удалять старые игры;
* менять настройки клуба;
* назначать администраторов;
* объединять/удалять игроков;
* выполнять импорт истории.

---

## 4.3. ADMIN — администратор клуба

Может всё, что статист, плюс:

* управлять игроками;
* исправлять любые исторические партии;
* отменять ошибочные партии;
* восстанавливать отменённые партии;
* управлять приглашениями;
* связывать Telegram-пользователя с существующим игроком;
* назначать других администраторов;
* импортировать старую статистику;
* экспортировать всю статистику;
* управлять настройками клуба.

Желательно поддерживать несколько администраторов.

# 6. Telegram-аутентификация

Отдельный логин/пароль не нужен.

Telegram уже идентифицирует пользователя через `telegram_user_id`.

При `/start` бот получает:

* Telegram User ID;
* username, если есть;
* first_name;
* last_name, если есть.

Номер телефона не нужен.

---

# 7. Player и Telegram User — разные сущности

Это важное архитектурное решение.

`Player` — человек в игровой статистике.

`TelegramUser` — Telegram-аккаунт.

Один Player может существовать без Telegram-аккаунта.

Это необходимо для импорта старой статистики.

Пример:

В старом Excel уже существует:

`Максим`

У него 84 исторические игры.

После запуска бота Максим впервые открывает `/start`.

Администратор связывает:

`Telegram @max123 ↔ Player "Максим"`

После этого Максим видит всю старую статистику как свою.

Нельзя автоматически создавать второго «Максима», если исторический Player уже существует и ожидает привязки.

---

# 8. Вступление в клуб

Новый Telegram-пользователь не должен автоматически становиться участником клуба.

Предусмотреть приглашение.

Предпочтительный вариант:

Telegram deep link:

`https://t.me/BOT_NAME?start=invite_TOKEN`

После перехода:

> 🎩 Secret Hitler Stats
>
> Вас приглашают в клуб
> **Saturday Hitler Club**
>
> [Вступить]

После вступления пользователь либо:

### Вариант A — новый игрок

Создать новый Player и привязать Telegram.

### Вариант B — человек уже есть в старой статистике

Показать:

> Возможно, вы уже есть в статистике.
>
> [Выбрать существующего игрока]
> [Я новый игрок]

Финальную привязку существующего Player желательно подтверждать администратору.

# 12. Создание игрового вечера

Если активного вечера нет, любой активный участник клуба может нажать:

**🍻 Начать игровой вечер**

Создавший вечер автоматически становится статистом.

Далее бот предлагает отметить присутствующих.

Пример:

> 👥 **Кто сегодня здесь?**
>
> ✅ Максим
> ✅ Андрей
> ⬜ Катя
> ✅ Дима
> ✅ Саша
> ✅ Никита
>
> Выбрано: 5
>
> [Начать вечер]

Минимальное количество участников непосредственно для партии — 5.

Сам вечер разрешается создать и при меньшем количестве, но кнопку записи партии необходимо заблокировать, пока для игры нет минимум 5 игроков.

---

# 13. Единственный активный вечер

Для одного клуба одновременно разрешён только один активный игровой вечер.

На уровне БД это должно быть защищено constraint/index, а не только UI.

Если Дима и Максим одновременно нажали «Начать вечер»:

первый успешный запрос создаёт вечер.

Второй получает:

> 🍻 Игровой вечер уже создан.
>
> Статист: Дима
>
> [Открыть вечер]

Не создавать два параллельных вечера.

> Сейчас: 8 игроков
>
> Для следующей партии:
>

Играли 8 человек.

>
> Сейчас: 7 игроков.
>
> Для следующей партии:
>
> 🔵 Liberals: 4

> 👑 Hitler: 1

Олег остаётся участником первых трёх партий.

# 17. Важное правило изменения состава

Практический flow вечера:

1. закончилась партия;
2. статист сначала записывает завершённую партию;
3. после сохранения бот спрашивает, изменился ли состав следующей партии;
4. только после этого добавляются пришедшие или убираются ушедшие.

После сохранения игры показывать:

> ✅ Игра #4 сохранена.
>
> **Состав следующей партии тот же?**
>
> [✅ Да]
> [👥 Изменился]

Это уменьшит вероятность ошибки, когда игрок ушёл после партии, но статист удалил его до сохранения только что сыгранной игры.

---

# 18. Snapshot состава партии

При сохранении каждой партии необходимо создавать отдельные записи `game_players`.

Нельзя при отображении старой игры брать текущий состав игрового вечера.

Пример:

Session:

* Game 1 — 8 игроков;
* Game 2 — 8;
* Game 3 — 8;
* Олег ушёл;
* Game 4 — 7;
* Ваня пришёл;
* Game 5 — 8.

Каждый Game хранит собственный состав.

# 19. Допустимое количество игроков

Официальная партия Secret Hitler рассчитана на 5–10 человек.

Распределение:

| Игроков | Liberals | обычных Fascists | Hitler |
| ------: | -------: | ---------------: | -----: |
|       5 |        3 |                1 |      1 |
|       6 |        4 |                1 |      1 |
|       7 |        4 |                2 |      1 |
|       8 |        5 |                2 |      1 |
|       9 |        5 |                3 |      1 |
|      10 |        6 |                3 |      1 |

Hitler НЕ входит в число обычных Fascists в третьей колонке.

То есть 10 игроков:

* 6 Liberals;
* 3 Fascists;
* 1 Hitler.

Всего 10.

Источник распределения — официальные правила Secret Hitler.

---

# 20. Если на вечере присутствует больше 10 человек

Система клуба не должна запрещать иметь больше 10 присутствующих.

Например в помещении 12 человек.

При записи партии бот должен попросить выбрать 5–10 участников конкретной игры.

Если текущих присутствующих ≤10, использовать весь текущий состав по умолчанию.

Если присутствующих >10:

> 👥 Сейчас присутствуют 12 человек.
>
> Выберите тех, кто участвовал в этой партии.
>
> Выбрано: 10/10

После выбора ролевая сетка рассчитывается именно от состава данной партии.

---

# 21. Запись завершённой партии

Главный сценарий статиста:

**➕ Записать игру**

Цель — максимально короткий flow.

---

# 22. Шаг 1 — состав

Если присутствует 5–10 человек:

по умолчанию использовать текущий состав.

Не заставлять статиста выбирать всех заново.

Можно показать маленький confirmation screen:

> 🎲 Игра #5
>
> Игроков: 8
>
> Максим, Андрей, Катя, Дима, Саша, Олег, Никита, Ваня
>
> [Состав верный]
> [Изменить]

Чтобы сделать ввод ещё быстрее, этот confirmation можно пропустить в первой версии и дать кнопку изменения состава непосредственно на экране выбора Hitler.

---

# 23. Шаг 2 — выбрать Hitler

Бот показывает всех участников партии:

> 👑 **Кто был Hitler?**
>
> [Максим]
> [Андрей]
> [Катя]
> ...

Можно выбрать ровно одного игрока.

---

# 24. Шаг 3 — выбрать Fascists

Бот уже знает количество Fascists.

Например 8 игроков:

нужно выбрать ровно 2 обычных Fascists.

Экран:

> 😈 **Выберите Fascists — 0/2**

После первого:

> 😈 **Выберите Fascists — 1/2**
>
> ✅ Андрей

После второго:

> 😈 **Выберите Fascists — 2/2**
>
> ✅ Андрей
> ✅ Катя
>
> [Продолжить]

Hitler не должен присутствовать в списке доступных Fascists.

Нельзя выбрать меньше или больше требуемого количества.

Проверка обязательно выполняется также на backend.

---

# 25. Liberals назначаются автоматически

Все участники партии, которые:

* не Hitler;
* не обычные Fascists;

получают роль `LIBERAL`.

Пользователь никогда вручную не выбирает Liberals.

---

# 26. Шаг 4 — победитель

Экран:

> 🏆 **Кто победил?**
>
> [🔵 Liberals]
> [🔴 Fascists]

---

# 27. Шаг 5 — способ победы

Если выбраны Liberals:

> 🔵 Как закончилась игра?
>
> [📘 5 либеральных законов]
> [🔫 Hitler убит]

Если Fascists:

> 🔴 Как закончилась игра?
>
> [📕 6 фашистских законов]
> [👑 Hitler избран канцлером]

По официальным правилам Liberals выигрывают после пяти Liberal Policies либо убийства Hitler; Fascists — после шести Fascist Policies либо избрания Hitler канцлером после третьей Fascist Policy.

Мы НЕ записываем количество законов по ходу партии.

Тип завершения — только итоговый факт.

Игрок очень рано правильно определил Hitler/Fascist или сделал особенно точный прогноз.

# 32. Руина

Руина является более важным статистическим событием, чем остальные моменты.

Для Руины дополнительно выбрать причину.

Категории:

* неправильное голосование;
* спалил / неправильно отыграл роль;
* неправильный выбор канцлера;
* неправильное убийство;
* сказал лишнюю информацию;
* тактическая ошибка;
* другое.

В коде использовать стабильные enum-коды, а не русские строки.

Например:

`WRONG_VOTE`

`ROLE_REVEAL`

`BAD_CHANCELLOR`

`BAD_EXECUTION`

`LEAKED_INFO`

`TACTICAL_ERROR`

`OTHER`

# 40. Аварийная смена статиста

Необходимо предусмотреть ситуацию:

* статист ушёл;
* телефон разрядился;
* пропал интернет;
* статист забыл передать права;
* администратора рядом нет.

Чтобы вечер не оказался заблокирован навсегда, предусмотреть резервный механизм.

Рекомендуемый вариант:

`⚙️ Проблема со статистом → Сменить статиста`

Новый кандидат выбирается среди текущих участников.

Для аварийной передачи нужны подтверждения минимум двух других текущих участников клуба.

ADMIN может сменить статиста без подтверждений.

Это аварийный сценарий и не должен занимать место на основном экране.

# 56. Удаление партий

Не использовать физический `DELETE` как стандартное действие.

Использовать soft delete / void.

Например:

`game.status = VOID`

Такая партия:

* не участвует в статистике;
* не участвует в рейтингах;
* не учитывается в счёте вечера;
* остаётся в базе;
* может быть восстановлена ADMIN.

# 59. Victory Type

Enum:

```text
LIBERAL_POLICIES
HITLER_KILLED
FASCIST_POLICIES
HITLER_CHANCELLOR
UNKNOWN
```

Для игр, введённых вручную через Telegram, `UNKNOWN` не разрешать.

Для старого Excel `UNKNOWN` разрешён, если исторические данные не содержат способ победы.

Validation:

```text
LIBERAL_POLICIES -> winner LIBERAL
HITLER_KILLED -> winner LIBERAL

FASCIST_POLICIES -> winner FASCIST
HITLER_CHANCELLOR -> winner FASCIST
```

Невалидное сочетание backend обязан отклонить.

# 64. Backend validations

Нельзя доверять Telegram UI.

При сохранении игры backend обязан проверить:

1. session существует;
2. session ACTIVE;
3. actor является statistician либо ADMIN;
4. игроков минимум 5;
5. игроков максимум 10;
6. все игроки принадлежат клубу;
7. все `player_id` уникальны;
8. Hitler ровно один;
9. Hitler является участником игры;
10. количество Fascists соответствует размеру партии;
11. Fascists уникальны;
12. Hitler не находится среди обычных Fascists;
13. оставшиеся игроки становятся Liberals;
14. winner валиден;
15. victory_type соответствует winner;
16. sequence_number уникален;
17. запрос не является повторным сохранением уже сохранённого draft.

# 65. Idempotency

Telegram callback может прийти повторно.

Двойное нажатие:

**Сохранить игру**

не должно создать две партии.

После первого успешного сохранения draft необходимо пометить как completed либо удалить.

На backend использовать idempotency token/draft id.

# 66. Game Draft

Во время мастера записи партии информация ещё не должна считаться официальной игрой.

Можно использовать:

`game_draft`

в памяти/FSM.

Так как приложение планируется запускать одним instance, допустим aiogram FSM `MemoryStorage` в MVP.

Но финальное сохранение Game должно происходить одной DB-транзакцией.

Если бот перезапустился во время заполнения:

пользователь просто начинает ввод партии заново.

Никакие полуготовые данные не должны попасть в статистику.

Если позже будет несколько instances — заменить FSM storage на Redis.

# 72. Handler не должен содержать бизнес-логику

Плохо:

```python
@router.callback_query(...)
async def save_game(...):
    # 150 lines validating roles,
    # calculating winners,
    # updating stats...
```

Хорошо:

```python
await game_service.create_game(
    actor=actor,
    session_id=session_id,
    participants=participants,
    hitler_id=hitler_id,
    fascist_ids=fascist_ids,
    winner=winner,
    victory_type=victory_type,
)
```

Handler занимается:

* получением Telegram input;
* вызовом service;
* отображением результата.

# 73. Callback Data

Не писать хаотичные строки вручную.

Использовать aiogram `CallbackData`.

Пример концептуально:

```text
session:start
session:view:<id>
roster:add:<player_id>
roster:remove:<player_id>
game:hitler:<player_id>
game:fascist:<player_id>
game:winner:L
game:victory:HK
game:save:<draft_id>
event:type:R
```

Помнить об ограничении Telegram callback data.

Не помещать туда большие JSON.

# 74. Статистика должна вычисляться запросами

Не хранить:

```text
players.total_games
players.total_wins

```

как источник истины.

Это создаёт риск рассинхронизации после редактирования старой партии.

Можно добавить cache/materialized views позднее, если когда-нибудь появится проблема производительности.

Для десятков тысяч игр PostgreSQL легко посчитает такую статистику.

# 76. Требования к importer

Importer должен:

* читать XLSX;
* желательно поддерживать CSV;
* показывать найденных игроков;
* создавать исторических Player без Telegram;
* обнаруживать похожие/одинаковые имена;
* не создавать дубль без предупреждения;
* валидировать количество игроков;
* валидировать роли, если они присутствуют;
* импортировать победителя;
* импортировать роль каждого игрока;
* импортировать дату, если она есть;
* поддерживать неизвестный тип победы;
* иметь dry-run;
* выдавать отчёт об ошибках;
* работать транзакционно.

Если строка некорректна:

не импортировать её молча.

Вывести причину.

# 105. Итоговая концепция MVP

Система должна ощущаться не как административная база данных, а как лёгкий помощник вашей компании.

**PLAYER**

смотрит игру и статистику.

**STATISTICIAN**

за несколько нажатий фиксирует результаты конкретного вечера.

**ADMIN**

редко вмешивается и занимается только клубом, историей и исправлением ошибок.

**BOT**

сам вычисляет всё, что способен вычислить без участия человека.

Именно эта простота является главным требованием проекта.
